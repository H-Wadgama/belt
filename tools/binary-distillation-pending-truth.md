# Binary Distillation Pending-Field and State-Truth Refactor Plan

## Objective

Fix the remaining workflow bug where the assistant can verbally claim that a field has been confirmed even though the authoritative stored engineering state was never updated.

Observed failure:

```text
Assistant:
Should the design use the optimum feed plate?

User:
Of course!

[calling get_binary_distillation_problem({})]

Assistant:
Optimum feed plate: Confirmed
```

But a later read showed:

```text
use_optimum_feed_plate = null
```

This means the assistant used conversational context to claim a state transition that never happened in the deterministic state.

The system must enforce:

> **The assistant may never claim that an engineering field was added, changed, confirmed, or derived unless that change exists in the authoritative deterministic state returned by a tool.**

The fix should introduce:

1. explicit **pending-field state**;
2. contextual handling of short replies such as “yes,” “of course,” “0.99,” etc.;
3. deterministic conversion of those replies into actual WRITE operations;
4. a strict **state-truth rule** for the final LLM response; and
5. explicit behavior once the workflow reaches `ready_for_calculation`.

---

# 1. Root Cause

The current READ/WRITE architecture is mostly correct:

```text
new engineering facts
    → WRITE

questions about existing state
    → READ
```

However, short contextual responses create a third situation.

Example:

```text
Assistant:
Should the design use the optimum feed plate?

User:
Of course!
```

The literal current user message contains no field name.

A generic intent classifier may therefore decide:

```text
no obvious engineering quantity
→ READ
```

But semantically the user is answering the field requested in the immediately preceding workflow state.

Therefore the workflow needs a deterministic representation of:

```text
"What specific information is the system currently waiting for?"
```

Do not rely only on conversation history for this.

---

# 2. Add Pending-Request State

Extend the authoritative workflow state with a pending request.

Conceptually:

```python
pending_request: dict | None
```

Example:

```python
pending_request = {
    "field": "use_optimum_feed_plate",
    "request_type": "boolean_confirmation"
}
```

When there is no outstanding question:

```python
pending_request = None
```

The pending request is part of the deterministic workflow state.

It should not exist only in Qwen's conversation history.

---

# 3. Pending Request Should Be Generated by the Workflow Checker

The deterministic workflow checker should identify the next unresolved field or field group.

Example:

All Case D requirements are complete except optimum-feed-plate confirmation:

```python
{
    "status": "need_optimum_feed_plate_confirmation",

    "missing_case_inputs": [],

    "pending_request": {
        "field": "use_optimum_feed_plate",
        "request_type": "boolean_confirmation"
    }
}
```

Then Qwen may phrase that naturally:

```text
Should the design use the optimum feed plate?
```

But the fact that this is the outstanding question comes from Python.

---

# 4. Resolve Pending Requests Before Normal READ/WRITE Classification

Change the per-turn routing hierarchy.

Current conceptual routing:

```text
User message
    ↓
READ / WRITE / mixed?
```

Change it to:

```text
User message
    ↓
Is there a pending request?
    │
    ├── YES
    │     ↓
    │  Can this message answer the pending request?
    │     │
    │     ├── YES → convert answer into WRITE
    │     │
    └─────└── NO  → normal READ / WRITE routing
    │
    └── NO
          ↓
      normal READ / WRITE routing
```

Pending-field resolution therefore has priority over ordinary turn classification.

---

# 5. Boolean Confirmation Handling

For:

```python
pending_request = {
    "field": "use_optimum_feed_plate",
    "request_type": "boolean_confirmation"
}
```

recognize affirmative answers such as:

```text
yes
yeah
yep
sure
okay
ok
of course
ofcourse
that's fine
do it
use it
absolutely
sounds good
```

These should become:

```python
update_binary_distillation_problem(
    use_optimum_feed_plate=True
)
```

Recognize negative answers such as:

```text
no
nope
don't
do not
don't use it
not necessary
no thanks
```

These should become:

```python
update_binary_distillation_problem(
    use_optimum_feed_plate=False
)
```

Do not merely report the interpretation in prose.

The WRITE must actually occur.

---

# 6. Handle Noisy Short Responses

The system should be reasonably tolerant of conversational noise.

The observed message was:

```text
Ofcourse!@
```

This should still resolve as affirmative.

Normalize lightweight punctuation/casing before classifying contextual confirmations.

Conceptually:

```python
normalized = normalize_short_reply(text)
```

For example:

```text
"Ofcourse!@" → "ofcourse"
"YES!!!"     → "yes"
"nope."      → "nope"
```

Do not perform aggressive semantic rewriting.

This normalization is only intended to make short confirmation parsing robust.

---

# 7. Generalize Pending Requests Beyond Boolean Fields

Although the immediate bug concerns `use_optimum_feed_plate`, design the mechanism generically.

Example:

```python
pending_request = {
    "field": "xD",
    "request_type": "float",
    "expected_units": None
}
```

Then:

```text
Assistant:
What is xD?

User:
0.99
```

should become:

```python
update_binary_distillation_problem(
    xD=0.99
)
```

Another example:

```python
pending_request = {
    "field": "pressure_Pa",
    "request_type": "quantity",
    "expected_units": "Pa"
}
```

User:

```text
101325
```

could then be interpreted in the requested context as:

```python
pressure_Pa=101325
```

provided the workflow deliberately asked for pressure in Pa.

---

# 8. Support Pending Field Groups Carefully

Sometimes more than one quantity is requested.

Example:

```text
Please provide xD and xB.
```

Represent this as:

```python
pending_request = {
    "fields": ["xD", "xB"],
    "request_type": "field_group"
}
```

If the user replies:

```text
0.99 and 0.01
```

the system may map them according to the explicitly stored request order:

```python
xD = 0.99
xB = 0.01
```

But if the response is ambiguous:

```text
0.99
```

do not guess which of two equally unresolved fields it belongs to unless the pending-request representation explicitly identifies one expected field.

Prefer requesting one field or a clearly ordered field group.

---

# 9. Clear Pending Requests After Successful Resolution

After:

```python
update_binary_distillation_problem(
    use_optimum_feed_plate=True
)
```

the workflow should reassess state.

If successful:

```python
pending_request = None
```

or advance to the next missing field.

Do not leave a stale pending request active.

Otherwise a later:

```text
yes
```

could accidentally update an already resolved field.

---

# 10. Pending Requests Must Be Invalidated When the Problem Changes

Suppose:

```text
pending_request = xD
```

and the user says:

```text
Actually, start over with ethanol and water.
```

The old pending request must be cleared.

Any substantial problem reset or component replacement should invalidate pending requests derived from the old problem.

Likewise, `reset_workflow_session()` must reset:

```python
pending_request = None
```

---

# 11. Add a State-Truth Rule for Qwen

Update the system prompt with a strict rule:

```text
The deterministic tool state is the sole authority for engineering facts.

Never claim that a field was supplied, confirmed, changed, or derived unless
the latest tool result shows that value in the authoritative state.

Conversation context may help interpret what the user means, but it does not
itself modify engineering state.

If a user confirms a pending field, you must perform a WRITE that records the
field before saying that it is confirmed.

Never say "confirmed", "updated", "stored", "specified", or equivalent unless
the returned tool state verifies the change.
```

This directly addresses the observed failure.

---

# 12. Final Response Must Be Grounded in Latest Tool Result

After every WRITE:

```text
User
  ↓
WRITE tool
  ↓
returned authoritative state
  ↓
tool-free synthesis
```

The synthesis model should describe **only the returned state**.

Example:

User:

```text
Of course!
```

Tool call:

```python
update_binary_distillation_problem(
    use_optimum_feed_plate=True
)
```

Tool output:

```python
{
    "use_optimum_feed_plate": True,
    "status": "ready_for_calculation"
}
```

Then Qwen may say:

```text
The optimum feed plate is now confirmed.

The Case D problem is fully specified and ready for the calculation stage.
```

If the tool instead returns:

```python
use_optimum_feed_plate = None
```

Qwen must not say it was confirmed.

---

# 13. Add Optional Deterministic Response Validation

Consider adding a lightweight guard before returning the final answer.

For fields whose state transitions matter, the orchestration layer can inspect the tool result.

Example:

```python
if tool_name == "update_binary_distillation_problem":
    authoritative_state = result["state"]
```

Then include an explicit synthesis instruction such as:

```text
Authoritative state after this turn:
use_optimum_feed_plate = True

Do not claim any engineering state not present in this object.
```

The LLM still writes the prose, but it is tightly grounded in the returned state.

---

# 14. Fix the `ready_for_calculation` Boundary

The workflow-only agent currently stops before engineering calculation.

Therefore, once:

```python
status = "ready_for_calculation"
```

do not say:

```text
Let me know if you'd like to proceed!
```

because this agent has no enabled calculation path.

Instead say something equivalent to:

```text
The binary-distillation problem is fully specified and ready for the
calculation stage.

This workflow-only agent stops at problem definition, so no distillation
calculation is performed here.
```

This avoids creating an unsupported conversational transition.

---

# 15. Handle "Proceed" After Ready State

Once:

```python
status = "ready_for_calculation"
```

and the user says:

```text
yes
go ahead
proceed
calculate it
do it
```

do not return a generic chatbot response.

The agent should recognize that the user wants to cross the current workflow boundary.

For the current implementation, return:

```text
The problem is ready for calculation, but this workflow-only agent is
intentionally limited to problem specification. The calculation layer is
not enabled here.
```

No new state mutation is necessary.

Later, when the deterministic calculation layer is intentionally connected, this can become a real transition.

---

# 16. Improve Case-D Messaging

Observed sequence:

```text
pressure = 101325 Pa
feed temperature = 350 K
V/B = 2
```

The assistant said:

```text
The problem is now ready for case specification.
```

This wording should be improved.

`V/B` is a distinguishing Case D variable.

The deterministic workflow should already identify:

```python
case = "D"
```

or:

```python
case_candidates = ["D"]
```

Therefore the assistant should say:

```text
The boilup-ratio specification identifies this as a Wankat Case D problem.

The remaining Case D inputs are:
- xD
- xB
- optimum-feed-plate confirmation
```

Do not ask the user to choose a case once the supplied engineering variables have already identified it.

# 17. Recommended Routing Order

The complete per-turn controller should now operate in this order:

```text
START USER TURN
      ↓
Is this an explicit RESET/new-problem request?
      │
      ├── YES → RESET/replace state as appropriate
      │
      └── NO
            ↓
Does authoritative state contain pending_request?
            │
       ┌────┴────┐
       │         │
      YES        NO
       │         │
       ▼         ▼
Can current   Normal
message       READ/WRITE/
resolve it?   mixed routing
   │
 ┌─┴─┐
 │   │
YES  NO
 │   │
 ▼   └─────────────► normal routing
WRITE resolved
pending field
 │
 ▼
normalize state
 │
 ▼
consistency check
 │
 ▼
workflow assessment
 │
 ▼
new pending_request
or ready state
 │
 ▼
TOOL-FREE FINAL RESPONSE
 │
 ▼
STOP
```

```python
    "prompt": "Please provide xD followed by xB."

```

The exact structure may differ, but it must be deterministic and serializable.

# 20. Important Invariant

Add this as an explicit architecture invariant:

```text
ASSISTANT CLAIM
      ↓
must be supported by
      ↓
LATEST AUTHORITATIVE TOOL STATE
```

Examples:

```text
"The pressure is 101325 Pa."
→ pressure_Pa must equal 101325 in state.

"The composition is 25% methanol."
→ composition must show 0.25 in state.

"The optimum feed plate is confirmed."
→ use_optimum_feed_plate must be True in state.

"The problem is Case D."
→ workflow.case must be D.

"The problem is ready for calculation."
→ workflow.status must equal ready_for_calculation.
```

Conversation memory alone is not sufficient evidence.

# 21. Final Architecture

The binary-distillation workflow should now separate:

```text
Natural-language interpretation
        ↓
Pending-request resolution
        ↓
READ / WRITE classification
        ↓
Authoritative state mutation or inspection
        ↓
Deterministic normalization
        ↓
Consistency validation
        ↓
Wankat workflow classification
        ↓
Pending next input OR ready state
        ↓
Tool-free grounded explanation
```

Responsibilities remain:

```text
Qwen
= understand language and communicate results

Python state manager
= remember the engineering problem

Pending-request layer
= connect short contextual answers to explicit engineering fields

Feed normalization
= derive mathematically determined quantities

Consistency checker
= reject contradictions

Wankat workflow engine
= determine case and missing specifications

Future calculation layer
= perform the actual distillation design
```

# 22. Definition of Done

This refactor is complete when:

- The deterministic state records what field the workflow is currently requesting.
- Short contextual responses can resolve that field.
- `"Of course!"` correctly writes `use_optimum_feed_plate=True`.
- `"No"` correctly writes `use_optimum_feed_plate=False`.
- A successful confirmation is visible in subsequent READ calls.
- The assistant never claims a state change that is absent from the authoritative state.
- Derived or conversational information cannot silently become stored engineering state.
- Pending requests clear or advance after successful resolution.
- Reset/new-problem operations clear stale pending requests.
- Numeric contextual answers can map to explicitly pending fields.
- Case D is recognized from its distinguishing boilup-ratio specification.
- `ready_for_calculation` is treated as the terminal state of the workflow-only agent.
- `"proceed"` after the ready state produces a clear workflow-boundary response.
- Existing READ/WRITE protections remain intact.
- Existing consistency checks remain intact.
- All previous workflow and orchestration tests continue to pass.
- New pending-request/state-truth tests pass.

The core rule is:

> **Conversation context can help interpret a user's answer, but only a successful deterministic WRITE changes engineering state. The assistant may describe only what the authoritative state actually contains.**
